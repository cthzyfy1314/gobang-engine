## 1. 背景与约束

### 1.1 比赛背景
- **赛事**：沈航校内计算机博弈大赛
- **比赛日期**：2026-05-10（周日）
- **棋种**：五子棋（Connect5），15×15 棋盘
- **规则**：完整国规（详见 1.4 节国规对照表）
  - **先后手确定**：抽签或猜先（赛前一次性，引擎不参与，由比赛现场决定）
  - **指定开局**（26 种：斜指 13 + 直指 13）；黑 1 必在天元（H8）；黑 3 限定围绕天元的 5×5 区域；选指定开局**同时**给出 N（五手 N 打的打点数量）
  - **三手交换**：白方在白 4 之前可选择换边一次（每盘只有一次机会，黑方必须同意）
  - **五手 N 打**：黑方按 N 给 N 个不同形候选点，白方挑一个作为黑 5
  - **三种禁手（黑方专属）**：三三禁手、四四禁手、长连禁手
  - **终局判负优先级**：
    - 先成五连者胜；白长连=五连胜
    - 黑禁手 → 白胜
    - **特殊：黑五连与禁手同时形成 → 禁手失效，黑胜**
    - **特殊：白方未"立即"指出黑禁手（已落白子）→ 该禁手不再成立**
  - **和棋条件**：双方放弃 / 全盘满无胜局 / 双方同时超时（最后一种本赛无时间限制不适用）

### 1.2 比赛形式（关键）
- **AI vs AI，但人当信使**——双方各跑自己的程序
- **没有自动协议总线**：对手下哪里 → 你看见后**手工**在自己程序里录入对方坐标 → 你程序算出应招 → 你**口头报**给对手 → 循环
- **裁决**：人眼判定（禁手由人裁判看）
- **时间限制**：**无**（但实战目标 5-10 秒/步以保持体面）

### 1.3 工程约束
- **可用开发时间**：**约 9 工作日**
  - 4/28 周二：半天（写 spec + 建仓 + 脚手架）
  - 4/29 周三、4/30 周四：满日开发
  - 5/1-5/5 五一：**晚上酒店内开发，每晚 0.5d**（共 2.5d）—— 用户 2026-04-28 确认
  - 5/6 周二、5/7 周三、5/8 周四、5/9 周五：满日开发
  - 5/10 周六：比赛日
- **Buffer**：约 1.5-2 天（用于联调 / 调参 / 自我对战 / bug 修）
- **语言**：C99 标准，单 exe，Windows 平台（沿用井字棋项目编译方式）
- **编译器**：MSVC，UTF-8 源码，`/utf-8` 编译选项
- **依赖**：仅 Windows 标准 API（`<windows.h>` `<stdio.h>` 等），无第三方库

**审核结论**：所有国规条款都有明确实现位置，无遗漏。

### 2.1 必达目标（P0）
- ✅ 完整国规规则实现，**不出现违规判负**
- ✅ 引擎自检禁手——下子前提示"如果下这里是禁手"，防己方误下

- ✅ 友好的 console GUI——录入对方坐标 / 显示己方建议 / 棋型威胁标注
- ✅ 单步响应时间**目标 5-10 秒**（实战体面，且无 timeout 强制）

### 2.2 加分目标（P1，时间充足，**全部纳入计划**）
- ✅ Zobrist 哈希置换表（搜索量降低 30-60%）— 0.5d

- ✅ VCF 算杀（连续冲四致胜）— 1d

- ❌ Gomocup / piskvork brain DLL 协议适配（比赛形式不需要）

- ❌ 自动裁判通信
- ❌ Linux/macOS 跨平台支持

## 3. 算法选型与理由

### 3.1 主算法：α-β minimax + 棋型评估

```
αβ minimax + 启发式排序
   ├─ 邻近 2 圈剪枝（搜索空间从 225 → 30 候选）
   ├─ Zobrist 哈希 + 置换表
   ├─ 迭代加深 + Killer Move
   └─ 完整禁手判定（黑专属）
```

**深度**：6-8 层基线，迭代加深可冲到 10-12 层（无时间压力）

### 3.2 评估函数：棋型识别（Pattern-Based）

按标准 Renju 棋型分类，分数表参考 xl-engine 实测：

| 棋型 | 分数 |
|------|------|
| 五连 | 100,000 |
| 活四 / 双冲四 / 双活三 | 10,000 |
| 冲四 / 活三 | 1,000 |
| 眠三 / 活二 | 100 |
| 眠二 | 10 |
| 活一 | 1 |

实现方法：6 格滑窗扫 4 方向（横/竖/正斜/反斜），落子时**只更新受影响的 4 条线**做 O(1) 增量。

### 3.3 算杀（P1）：简化 VCF

只搜冲四链——分支因子极低（5-10 个冲四点），可搜到 20-30 层深。检测到必胜手立即终止主搜索。

### 3.4 禁手判定算法

参考 `Desktop\gobang_refs\renju_forbid\renju_forbid.go`（聚焦禁手 800 行 Go 代码）+ `xl-engine\xl_ai.cpp:1025 XlIs33F`（产品级实现）双对照。

#### 三种禁手定义（黑方专属，对应国规第 8 条）

| 禁手 | 形成条件 | 难度 |
|------|---------|------|
| 长连禁手 | 一手形成 ≥6 子连子 | ⭐ |
| 四四禁手 | 一手同时形成 ≥2 个冲四以上 | ⭐⭐ |
| 三三禁手 | 一手同时形成 ≥2 个**真活三** | ⭐⭐⭐ |

#### 三三禁手"真活三"判定（最关键）

判某条三是不是"真活三"需要嵌套：
1. 假设黑方在三的延伸点继续落子
2. 该子能形成活四
3. **且**该延伸点本身不是禁手（递归调用 is_forbidden）

#### 关键边界规则（必须代码实现，对应国规第 9.2 条）

```c
// forbid.h API 设计
typedef enum {
    FORBID_NONE = 0,
    FORBID_DOUBLE_THREE = 1,
    FORBID_DOUBLE_FOUR = 2,
    FORBID_OVERLINE = 3,
} ForbidType;

// 落子后判定本步是否禁手或胜利
// 返回值优先级：胜利 > 禁手 > 无
typedef enum {
    RESULT_NONE,
    RESULT_BLACK_WIN,      // 黑五连，包括"黑五连+禁手同时"特例
    RESULT_WHITE_WIN_NORMAL, // 白五连
    RESULT_WHITE_WIN_BY_BLACK_FORBID, // 黑禁手→白胜
} GameResult;

GameResult check_after_move(Board *b, Move *m);
// 实现要点：
// 1. 先检查是否形成五连（黑或白）
// 2. 黑方落子若同时形成五连+禁手 → 五连优先（禁手失效，黑胜）
// 3. 仅当无五连且黑方时才检查禁手
```

**这个优先级顺序绝不能错**——它是国规 9.2 黑五连+禁手同时形成 → 禁手失效黑胜的唯一正确实现方式。

### 4.1 模块职责（9d 总预算下分配）

| 模块 | 主要职责 | 估时 | 风险 | 优先级 |
|------|---------|------|------|--------|
| `board` | 棋盘 (15×15 int 数组) + 落子/撤子 + 胜负判定（黑长连负 / 白长连胜不对称）| 0.5d | 低 | P0 |
| `pattern` | 棋型识别（活四/冲四/活三/眠三/活二...）+ 评估函数 — **直接抄 xl-engine 棋型表**，不重新设计 | 1d | 中 | P0 |
| `search` | αβ minimax + 邻近 2 圈候选 + 基础 move ordering（按棋型分排序）| 1d | 中 | P0 |
| `forbid` | 三三禁手（递归判定）/ 四四禁手 / 长连禁手 | 1.5d | **高** | P0 |
| `opening` | 26 种指定开局表 + 三手交换决策 + 五手 N 打候选生成 | 0.5d | 低 | P0 |
| `ui` | console 绘制 + 录入对方坐标 + 显示己方建议 + 禁手警告 + 棋型威胁标注 | 1d | 低 | P0 |
| **P0 合计** | | **5.5d** | | |
| `zobrist` | Zobrist 哈希 + 置换表 | 0.5d | 低 | P1 |
| `search+` | 迭代加深 + Killer Move + History Heuristic | 0.5d | 低 | P1 |
| `vcf` | 简化 VCF 算杀（仅冲四链）| 1d | 中 | P1 |
| **P1 合计** | | **2d** | | |

**预算分配**（9d 总预算）：5.5d P0 + 2d P1 + **1.5d buffer**（联调 + 调参 + bug 修）。

**P1 已纳入第 7 节节奏**——zobrist+search+ 安排在 5/1-5/2 五一晚，VCF 安排在 5/8。如果中途 P0 模块超时，VCF 会被首先砍掉（第 7.1 节风险应对）。

**关键策略**：**靠"高效抄"压缩**——pattern/forbid/opening 都从 `Desktop\gobang_refs\` 三个参考仓库翻译过来，不从零设计。我（Claude）做翻译+注释工作，用户只做调参和测试。

## 5. 关键数据结构

### 5.1 Board

```c
#define BOARD_SIZE 15
#define EMPTY  0
#define BLACK  1
#define WHITE  2

typedef struct {
    uint8_t cells[BOARD_SIZE][BOARD_SIZE];  // 0/1/2
    uint8_t move_count;                      // 已落子数
    uint64_t zobrist_hash;                   // 当前哈希
    int      side_to_move;                   // 1=BLACK, 2=WHITE
    Move     history[BOARD_SIZE * BOARD_SIZE]; // 落子历史，撤子用
    bool     forbid_enabled;                 // true=完整国规模式（默认）；false=测试用（对样例代码时关闭）
} Board;

typedef struct {
    int8_t row, col;
    int8_t color;
} Move;
```

### 5.2 棋型缓存

每条线（横/竖/2 斜对角）维护一个棋型识别缓存。每条线长度 ≤15，可编码为 30 bit（每位 2 bit）→ 查表得棋型。

### 5.3 置换表

```c
typedef struct {
    uint64_t hash;
    int      depth;
    int      score;
    uint8_t  flag;    // EXACT / LOWER_BOUND / UPPER_BOUND
    Move     best_move;
} TTEntry;

#define TT_SIZE (1 << 20)  // 100 万条 entry, ~32MB
TTEntry tt[TT_SIZE];
```

### 5.4 开局库

```c
typedef struct {
    char     name[16];     // "斜指1" / "直指1" 等
    Move     moves[3];     // 黑1 / 白2 / 黑3 三手
} OpeningEntry;

OpeningEntry openings[26];
```

## 6. 接口设计：人肉协议下的对战流程（严格按国规）

**前提**：人当信使。引擎是"决策助手 + 棋盘可视化"，不直接通信。

下面分**执黑剧本**和**执白剧本**两种完整流程，每个阶段标注国规对应条款。

### 6.1 执黑剧本（按国规 4/6/7/8/9）

```
═══ 阶段 0：开局选择（国规 4——黑方决定前 3 子 + N） ═══

程序：你执黑还是执白？
你：黑

程序：选哪种指定开局？同时输入 N（五手 N 打候选数）：
       ┌────────────────────────────────────────┐
       │ 斜指开局（13 种，黑3 走斜方向）          │
       │   1) 寒星  → H8 / I9 / I7              │
       │   2) 溪月  → H8 / I9 / H6              │
       │   3) ...                               │
       │ 直指开局（13 种，黑3 走直方向）          │
       │   14) ...                              │
       └────────────────────────────────────────┘
       注：N 必须 ≥1 且 ≤"该开局可生成的不同形候选数"
你：1 5    （选寒星，N=5）

═══ 阶段 1：前 3 手自动落子（国规 4） ═══
程序：寒星已锁定，N=5。
        [自动落黑1=H8（天元）]    ← 国规 4：黑1 必在天元
        [自动落白2=I9]            ← 国规 4：白2 由黑方决定
        [自动落黑3=I7]            ← 国规 4：黑3 在天元 5×5 区域内

═══ 阶段 2：三手交换（国规 6——白方决定，每盘一次） ═══
程序：黑3 已下。等待对方（白方）决定是否使用三手交换权。
        请输入对方决定：
        1) 不交换（你继续执黑）
        2) 要交换（你方变白方，对方变黑方）
你：1     （对方说不交换）

═══ 阶段 3：白4（国规 4——白方落子） ═══
程序：等待对方下白4，输入对方坐标：
你：J8

═══ 阶段 4：五手 N 打（国规 7——黑方给候选 / 白方挑） ═══
程序：[绘制棋盘] 4 手已下。
        现在是黑5——按 N=5，引擎计算 5 个不同形候选：
        [思考 8 秒]
        候选 1: K10  评分 9200  ★（推荐）
        候选 2: G7   评分 8800
        候选 3: J11  评分 8500
        候选 4: H10  评分 8100
        候选 5: F8   评分 7900
        请把这 5 个位置都报给对方（白方），由白方挑一个作为黑5。
        对方挑了哪个？
你：3     （对方挑 J11）

═══ 阶段 5：正常对局（国规 8/9——禁手 + 终局判定） ═══
程序：黑5=J11 已落。等待对方下白6...
        [接下来回合制循环]
        
循环每回合（己方 = 黑方）：
   1. 引擎搜索 → 显示"建议下 H7 ★（评分 5200，活三*1）"
   2. ⚠️ 自检禁手（国规 8）："警告：你也可下 G9，但 G9 是三三禁手，已自动排除"
   3. 等用户回车采纳建议 / 输入其他坐标
   4. 落子后检查终局（国规 9）：
      - 形成黑五连？→ 显示"你赢"（即使同时是禁手也胜，国规 9.2-c）
      - 否则形成禁手？→ 显示"你违规判负"（一般不会到这——引擎搜索时已排除禁手位置；只有当用户**手动输入**了引擎警告过的禁手位置时才触发）
   5. 等用户录入对方白6，引擎更新棋盘
   6. 显示对方棋型威胁（"对方刚形成活三 J9-K10-L11，建议堵在 I8"）
   7. 检查白方终局（国规 9）：
      - 白形成五连或长连 → 显示"对方赢"（国规 9.1：白长连=五连）
   8. 继续下一回合
```

### 6.2 执白剧本（与执黑对称翻转）

```

你：白

程序：好。等待对方（黑方）选定指定开局并报给你...
```

### 6.3 白方"立即指出"黑方禁手的处理（国规 9.2-b）

国规：白方在黑方下禁手后必须**立即**指出，否则禁手不再成立。这意味着如果你执白且引擎检测到对方刚下了禁手，**必须在你下白子之前提示**：

```
程序：[对方刚下黑K7]
        ⚠️ 禁手警告：对方黑K7 形成三三禁手（活三 H7-I7-J7 + 活三 K5-K6-K7）
        按规则你必须立即指出，否则禁手不再成立！
        
        你要：
        1) 指出禁手 → 立即判对方负，本局结束
        2) 不指出，继续走白子（视为放弃禁手判定）
你：1

程序：对方违规判负。你赢了！
```

如果你选 2 → 引擎不再追究本次禁手；对方的"禁手"在 board 上视为合法落子，继续对局。

### 6.5 输入约定（坐标格式）

- **标准格式**：字母+数字，例如 `H8`、`J11`、`A15`（A-O 列，1-15 行）
- **大小写兼容**：`h8` 和 `H8` 等价
- **错误输入**：非法坐标 / 已占位置 → 提示重输，不退出
- **特殊输入**：
  - `?` → 显示帮助
  - `back` → 撤一回合（撤回最近双方各 1 步，防你打错对方坐标）；`back 1` 撤一手；`back N` 撤 N 步
  - `quit` → 退出（保存当前局面到 `data/replays/`）
  - 空回车 → 采纳引擎建议

## 8. 测试策略

### 8.1 单元测试（按国规对应必做）

#### `board` 模块
- 落子/撤子可逆（apply 后 undo 等价于未落子）
- 胜负判定**不对称**（对应国规 9.1）：
  - 黑 5 连续 → 黑胜 ✅
  - 黑 6 连续（长连）→ **黑负** ✅
  - 白 5 连续 → 白胜 ✅
  - 白 6 连续（长连）→ **白胜**（"长连视同五连"）✅

#### `pattern` 模块
- 每种棋型识别正确（活四 / 冲四左/右两种 / 跳活三 / 眠三 / 活二...）
- 边界条件：靠墙的棋型（A 列、O 列、行 1、行 15）不应误判为活的

#### `forbid` 模块（**最关键，对应国规 8/9.2**）
**标准 case**：
- 三三禁手：黑下后形成两个真活三 → 判禁手
- 四四禁手：黑下后形成两个冲四 → 判禁手
- 长连禁手：黑下后 ≥6 连 → 判禁手

**边界 case（必须全覆盖）**：
- ✅ **黑五连+禁手同时形成 → 五连优先（黑胜，国规 9.2-c）**
- ✅ 假活三（延伸点本身是禁手 → 不算真活三 → 不构成三三禁手）
- ✅ 嵌套三三（递归正确终止）
- ✅ 白方下棋同样位置 → 不判禁手（白方无禁手）
- ✅ 长连+四四同时形成 → 长连优先（按禁手类型优先级，国规 8 没明确，按 RIF 标准）

#### `search` 模块
- minimax 在终局位置返回正确分数
- αβ 剪枝结果与裸 minimax 在浅深度（≤4）下等效
- 黑方搜索时**不能选禁手位置**（即使评分再高）

### 8.2 集成测试

#### 完整对局回归
- 执黑 vs 自己执白：对完不出错（无段错误、无死循环）
- 完整国规流程跑通：从指定开局选择 → 三手交换 → 五手 N 打 → 正常对局 → 终局判定，每个阶段功能正常

#### 国规边界场景（人造局面测试）
- **场景 1**：构造一个"黑下下一步同时形成五连和三三" → 验证判定为黑胜
- **场景 2**：构造"黑活三+白即将活四" → 验证 search 选防而不是攻
- **场景 3**：执白录入对方刚下的禁手位置 → ui 提示"立即指出"选项
- **场景 4**：26 种指定开局每种都跑一遍前 5 手 → 验证 opening 表无错

#### 对战测试（两种模式）
- **棋力评估模式**（关禁手 + 关指定开局，对方=沈航 2017 样例）：胜率 ≥ 90%
  - 这条是测**纯算法棋力**——样例不带禁手，必须公平对比
  - 通过 `Board.forbid_enabled = false` 切换
- **完整国规模式**（带禁手 + 带指定开局，对方=本引擎自己）：100 局自我对战
  - 测**国规规则正确性**——黑方有禁手限制，先手优势抵消，黑胜率应 ≈ 50%
  - 这条不是测棋力，是测规则实现是否对称合理

### 8.3 性能基线
- NPS（Nodes Per Second）：开局阶段 ≥ 10 万（搜深度 8）
- 单步响应：终盘阶段 ≤ 10 秒（搜深度 8 + VCF）
- 内存：< 100MB（置换表 32MB + 棋盘缓存）
